# 定时续火花：行为逻辑与实现

> 记录时间：2026-11-17 | 设备：Xiaomi Mi 10 (umi) / Android 13 (API 33) / KernelSU

## 一、需求

三段，缺一不可：

1. 到设定时间把抖音启动起来
2. 自动续火花
3. 关闭抖音

**约束**：不加参数就不打扰用户 —— 不亮屏、不响铃、不需要解锁。

**前提**：手机已 root（KernelSU / Magisk），模块 App 已获 root 授权。

## 二、行为流程

```
系统闹钟 12:00（RTC_WAKEUP）
    │
    ▼
[模块进程] AlarmReceiver.onReceive
    │  ① 显式广播 → 模块进程被杀也会被系统 fork 起来（自举）
    │  ② 立即排下一天的闹钟（不等发送结果）
    │  ③ 抱 3 分钟 WakeLock（覆盖后面 20～60 秒）
    │  ④ root + monkey 拉起抖音
    ▼
[抖音进程] LSPosed 注入 Application.attach
    │  ⑤ scheduleOnAppStart() 无条件执行
    │  ⑥ shouldCheckNow() 时间闸门（12:00 → 窗口 11:50–18:00）
    │  ⑦ refreshSnapshot() 探测 IM 就绪，最长 60 秒
    │  ⑧ runRenew() 筛选 + 发送
    │  ⑨ markSent() + markRunDay() 落盘
    ▼
[模块进程] watchAndClose 线程
    │  ⑩ 每 10 秒读 spark_last_auto_day
    │  ⑪ 读到今天 + 等 3 秒 → am force-stop 关闭抖音
    ▼
结束。屏幕全程没亮。
```

## 三、关键设计决策

### 3.1 为什么用 monkey 而不是 startActivity

`startActivity` 在后台会被系统拦。证据在 `dumpsys alarm`：

```
idle-options=Bundle[{
    android.pendingIntent.backgroundActivityAllowed=false,
    ...
}]
```

`monkey -p <pkg> -c android.intent.category.LAUNCHER 1` 走 AMS 的注入通道，
不受这个限制。实测：

| 方式 | 屏幕 | stopped 清除 | 结果 |
|---|---|---|---|
| `am start` | **亮屏** | ✅ | 可能被 BAL 拦 |
| `monkey` | **不亮屏** | ✅ | 稳定 |
| `content query` provider | 不亮屏 | ✅ | 进程起来但 IM 不初始化 |

monkey 只接受 root 或 shell 身份。普通 App 身份执行会被 `Killed`：

```
su 10276 -c "monkey -p ... 1"   → Killed
su 0     -c "monkey -p ... 1"   → Events injected: 1
```

所以代码里 `RootShell.monkeyLaunch()` 先检查 `hasRoot()`，没有就直接失败 —— **不降级到 `startActivity`**。
降级会亮屏、打断用户正在用的应用，且大概率被 BAL 拦掉，属于「看着像在工作其实不可靠」。

### 3.2 为什么关闭动作放在模块进程

「发完杀抖音」如果写在抖音进程内，就是**进程自己杀自己**：

```
runRenew → ImMsgBridge 发送 → markSent 写配置 → markRunDay 写文件 → killProcess
                                                ↑
                                          竞态窗口在这里
```

`markSent` 和 `markRunDay` 是两次独立写入，中间被 kill 会导致「今天已发」没记上，
第二天重复发送。

放在模块进程里，判据是 **`spark_last_auto_day` 这个文件真的变成了今天** ——
这是已经落盘的事实，没有竞态。

### 3.3 为什么闹钟能自举

`PendingIntent` 是显式广播：

```kotlin
PendingIntent.getBroadcast(
    context, REQUEST_CODE,
    Intent(context, AlarmReceiver::class.java).setAction(ACTION_ALARM),  // ← 显式
    FLAG_UPDATE_CURRENT or FLAG_IMMUTABLE
)
```

闹钟响时系统检查 `AlarmReceiver` 所在进程，不在就 fork 一个新的。
所以模块进程被 LMK 杀掉、被系统回收、崩溃 —— 都不影响下一天的闹钟。

**唯一的死法**是 `force-stop`：它同时做两件事，设 `stopped=true` + 清空该 uid 全部闹钟。
闹钟没了，自举就没了。

### 3.4 时间闸门

`SparkConfig.checkAtAlarmOnly: Boolean = true`，默认开启。

```kotlin
private const val ALARM_WINDOW_AFTER_MS = 6L * 60 * 60 * 1000   // 设定点 +6h
private const val ALARM_WINDOW_BEFORE_MS = 10L * 60 * 1000      // 设定点 -10min
```

设 12:00 → 窗口 11:50–18:00。窗口内打开抖音会检查，窗口外不检查。

三种情况一律放行：开关关着 / 没设闹钟时间 / 配置读不到。

接在两处：
- `AutoSparkBridge.scheduleOnAppStart()`（每次抖音冷启动）
- `AutoSparkBridge.scanOnForeground()`（每次切回前台）

## 六、能力边界

| 场景 | 模块能自救吗 | 说明 |
|---|---|---|
| 模块进程被 LMK 回收 | ✅ | 闹钟是显式广播，会 fork 新进程 |
| 模块 App 崩溃 | ✅ | 同上 |
| 重启手机 | ✅ | `BOOT_COMPLETED` 重排闹钟 |
| 抖音被 force-stop | ✅ | monkey 能清 `stopped` |
| 抖音被清后台 | ✅ | monkey 直接拉起 |
| 进入 Doze | ✅ | `RTC_WAKEUP` + `setExactAndAllowWhileIdle` |
| **手动一键清理** | ❌ | 闹钟被一起清空，需手动开一次 App |
| **手动上滑清理** | ❌ | 同上（会先解多任务锁定再杀） |
| 卸载重装 | ❌ | 配置在 `/data/data`，卸载即丢 |
| 清除数据 | ❌ | 同上 |

### MIUI 开关实际作用

| 开关 | 挡 OneKeyClean | 挡 SwipeUpClean | 挡内存压力 |
|---|---|---|---|
| 多任务锁定 | ✅ | ❌（会先解锁定） | — |
| 电池无限制（bucket=5） | — | — | ✅ |
| 自启动 MIUIOP(10008) | — | — | — |
| 后台隐藏 | 纯展示 | 纯展示 | — |

**实测结论**：`OneKeyClean` 在锁定状态下没杀模块（19:31:16 那次的杀单里没有它）；
`SwipeUpClean` 显式杀了（18:44:28）。

### 自动清理从未发生

- `logcat -b events` 里 `LockScreenClean` 出现 **0 次**
- `com.miui.powerkeeper` 的 `night_clean_process` / `kill_app_switch` / `screen_off_clean_app` **全是空字符串**
- 结论：**当前设备上唯一的杀手是「手动上滑」和「手动一键清理」**

## 九、踩过的坑（每次改这块都要复查）

### 9.1 「发完关闭」的判据不能用文件内容

第一版 `watchAndClose` 判的是 `spark_last_auto_day` 的内容等于今天。**这是错的**：
同一自然日里抖音只要被打开过一轮，这个文件已经是今天了。闹钟再响一次时，
第一次轮询（10 秒）就判定「完成了」，直接把还在冷启动的抖音杀掉。

实测证据：

```
23:01:00.735  SparkAlarm: 闹钟触发：拉起抖音 MONKEY
23:01:00.888  onModuleLoaded
23:01:13.821  am_kill: com.ss.android.ugc.aweme
→ 只活 12.9 秒，一条消息都没发
```

正确判据是 **mtime 在本次闹钟之后变大**：

```kotlin
val baseline = RootShell.modifiedAt(DAY_FILE)   // 响铃前
val method = DailyAlarm.launchDouyin()
watchAndClose(baseline)                          // 等 mtime > baseline
```

修完实测：

```
23:25:00.782  基线 mtime=1794928557000
23:25:17.131  续火花结果：已发 0 / 跳过 4 / 失败 0
              mtime: 1794928557 → 1794929117
              aweme=0  wake=Asleep
```

### 9.2 通用教训

- **凡是「等某个副作用发生」的判据，都要用「相对本次触发的变化量」，不能用「当前值等于目标值」。**
  后者在「上一天/上一轮已经达到目标」时立刻假阳性。
- 判据要挑**最后写**的那个信号。这里 `markSent`（配置）和 `markRunDay`（文件）是两次独立写入，
  文件在后，所以等文件。反过来等配置会早关。
- 超时也要关抖音：它是 monkey 拉起来的，不是用户开的，留着会停在界面上。
